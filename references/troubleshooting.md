# 故障自愈

按现象查表。所有查询与重切的前提都是"索引与源文件一致"—— 校验做法见 `lookup-workflow.md` 步骤 1。

## 哈希不匹配（源文件已漂移）

`head -1 manifest.jsonl` 里的 `sha1` 与源文件实际哈希不一致。

- **只重切漂移的源**，不要全量重建：`sources[]` 逐源独立记录哈希，就是为了能只动漂移的那一个。
- 直接跑 `node split-dts.mjs`（不写 `--target`）即为增量自愈：逐源比对、只重切漂移项。
  命令与取舍见 `regenerate.md`。
- **在重切完成前，不要采信旧索引的结论** —— 分片可能已与源文件不符，查到的定义未必是当前的。

## 符号查不到

按可能性从高到低排查：

1. **该类型是新增的**（生成后又加了蓝图、或换了引擎 / 插件版本）→ 索引过期，重切对应源。
2. **`kind` 用错了**：`name` **不唯一**，同名不同类型的符号确实存在。查询键是 `(name, kind)`；
   只按 `name` 搜会命中多行，取错行就会误判成"查不到"。字段语义见 `manifest-spec.md`。
3. **搜错了文件**：索引在 `manifest.jsonl` 里，不在分片里。分片只有声明原文，没有 `src` / `kind` 字段。
4. 上述都不成立 → manifest 可能已损坏或被截断，见下方两条。

## 片内行号漂移 / 片名与预期不符

重切会改变装箱结果，**分片名与片内行号都会变**（某个常规片可能因此改号，例外片的编号同理）。

- 这是**已知且可接受**的行为：manifest 才是唯一权威的定位依据，分片名仅供人读。
- **不要**缓存上一次查到的片名 / 行号，每次都从 manifest 现查。
- 症状：按旧行号 `Read` 到的位置不是目标符号 → **以符号名二次定位**：
  分片头部注释列出了本片的单元清单，正文里的声明行也可直接搜；
  用符号名在候选分片里重新定位，而不要相信旧行号。

## `.fragments/` 里出现了 `.d.ts` 或 `.ts` 文件

**立即删除**，并查清是什么东西写进去的。

- `.fragments/` 位于 `Typing/` 下，宿主 `tsconfig.json` 的 `typeRoots: ["Typing"]` 会自动加载
  其下**任何** `.d.ts` —— 落进去的 `.d.ts` 会直接污染编译。这正是产物统一用 `.d.txt` 后缀的原因。
- 该目录的正常内容只有两类：`manifest.jsonl` 与 `*.d.txt` 分片。

## manifest 行数骤减（最危险的失效模式）

**症状**：某次运行后 `manifest.jsonl` 的行数明显变少，而**没有任何报错**。

- **含义**：增量执行的"读-改-写"被实现成了**整体重写** —— 本来只重切了一个源，却把其它源的行全丢了。
  manifest 是**单一文件**，而 meta 首行记录**全部源**的哈希，"只重切一个源然后整体重写"看起来合理，
  代价却是静默丢掉其余源的全部符号行。
- **后果**：之后查那些源的任何符号都查不到，且脚本不会报错 —— 属于"不报错的错"。
- **处置**：立即全量重建，并核对重建后的行数与内容是否恢复。

## manifest 首行非法 / 缺失

- 首行不是合法 JSON，或结构里没有 `sources[]` → 脚本判定为损坏，按"全量重建"处理。
- 更隐蔽的一种：文件**恰在行边界**处被截断 —— 首行 meta 完好、`sha1` 全部匹配，
  只是行少了若干。它同样不报错，靠上面的"行数骤减"识别。
- 处置：全量重建（见 `regenerate.md` 的强制全量判据）。

## 需要重新生成 `.d.ts` 本身

本技能做不到，任何命令行 / CI 流程也做不到 —— 生成入口是引擎编辑器内的代码生成命令。
回编辑器的操作方式与原因见 `regenerate.md` 末节。
